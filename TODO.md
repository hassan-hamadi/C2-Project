## Reliability and bug fixes

Things that are broken. A dead implant evades nothing.

| Surface | Risk | Status | Fix |
|---|---|---|---|
| No HTTP client timeout | `transmitSecureTelemetry` uses `http.Post` with no deadline, and the `get` and `download` paths use the same deadline-less client. A stalled or held connection freezes the request until the peer closes it: during the Xray blackhole debugging the agent hung silently for the full blackhole period. A forever-stalled transport means a dead implant with no visible reason | ❌ Planned | Per-request deadlines: a short context deadline on the envelope posts, a longer one on file transfers. A blanket `http.Client.Timeout` would kill large `get` uploads mid-flight on slow links, so the timeout must be per request class (or land chunked transfers first, after which one uniform timeout is safe) |

## Network evasion

What the wire shows: transport selection, TLS shape, timing, and volume.

| Surface | Risk | Status | Fix |
|---|---|---|---|
| VLESS + REALITY + uTLS transport | Go's TLS stack produces a distinctive JA3 hash regardless of HTTP-layer spoofing. A defender correlating JA3 against the claimed User-Agent sees Chrome headers over a Go TLS handshake, a contradiction no real browser produces | 🟡 Partially fixed | REALITY mode integrates uTLS with browser-family ClientHello presets (Chrome, Firefox, Safari) selected at build time from the dashboard browser profile. The agent authenticates to an Xray REALITY inbound via an X25519-authenticated SessionID blob inside the uTLS ClientHello, then sends a VLESS v0 TCP request for `127.0.0.1:5000` and carries the existing HTTP application protocol through the tunnel. Live-verified end to end against Xray-core 26.10.29 on a Linux agent. Remaining work: a live Windows session has not yet been recorded, direct HTTP and pinned HTTPS transports still use Go's native TLS stack, and no version-matched packet capture has compared the ClientHello against the real browser baseline |
| DNS-less connection to the edge | The agent dials the edge by IP while presenting the decoy domain as SNI. No DNS resolution before the connection is a standard beaconing indicator, and NDR runbooks treat bare-IP flows as their own category. Real browsers resolve names first | ❌ Planned | Resolve the decoy domain at connect time, the way a browser would, then dial the edge, so DNS matches the SNI. Resolving the edge's own domain instead trades one flag for another: the resolved name would not match the SNI. Honest limit: the destination IP still belongs to a datacenter rather than the decoy, visible to anyone pivoting on the IP, and that is inherent to REALITY's threat model. The agent already accepts hostnames, so this is mostly an operational change plus a few lines |
| Bounded jitter | Traffic never exceeds `JitterMax` and never drops below `JitterMin`. That bounding box is a weak signature: given enough observation time, statistical analysis can extract the range and flag it as non-human patterned traffic | ❌ Planned | Replace uniform random with long-tailed distributions (log-normal or exponential gaps between check-ins), randomize request padding, and slow the beacon down during idle periods. Full mimicry of a specific app (Windows Update, Slack) stays a stretch goal: copying cadence without the rest of that app's traffic just builds a new detectable hybrid, and Slack cadence on a host that doesn't run Slack is its own anomaly |
| Large file transfers | A `get` upload posts the entire file as one multipart body (up to the 100MB limit, with the whole file held in agent RAM). Beacon detection runbooks specifically flag outlier flows with disproportionately large payloads as the moment a tasking channel became data transfer. One constant-rate blob next to small periodic POSTs is exactly that outlier | ❌ Planned | Protocol work, not a tweak: chunked, rate-limited transfer spread across check-ins with randomized timing and padding, since the current `get` model returns a single result. Interim mitigation is operational discipline: don't `get` large files. Chunking also fixes the whole-file-in-RAM behavior |
| Beacon frequency | Fixed-interval polling is trivially flagged by most network analysis software | ✅ Fixed | Range-based jitter, where the agent sleeps a random duration between `JitterMin` and `JitterMax` each cycle |
| User-Agent fingerprint | Default `Go-http-client/1.1` User-Agent is a high-confidence IOC; mismatched headers create detectable "HTTP chimeras". Using a placeholder version like `Chrome/147.0.0.0` is itself a fingerprinting tell, real Chrome never ships as `X.0.0.0`. Sending `Sec-Fetch-Mode: navigate` on a JSON POST is a logical impossibility that real browsers never produce | ✅ Fixed | Five validated browser profiles (Chrome/Win, Chrome/Linux, Firefox/Win, Firefox/Linux, Safari/macOS) applied via a `UATransport` RoundTripper. Each profile includes the correct UA string, `Sec-Ch-Ua` client hints, `Sec-Fetch-*` metadata, and `Accept` values matching the April 2026 browser baseline. Chrome profiles use the real stable build string (`147.0.7727.55`) and the correct `Not-A.Brand` version (`v="24"`), not the placeholder `X.0.0.0` / `v="99"` pattern that fingerprinting tools flag. The transport layer automatically switches to fetch context (`Sec-Fetch-Mode: cors`, `Sec-Fetch-Dest: empty`, `Sec-Fetch-Site: same-origin`) on POST requests and drops navigation-only headers (`Upgrade-Insecure-Requests`, `Sec-Fetch-User`) that would be anomalous on a JSON API call |
| Transport security | All traffic is unencrypted HTTP, visible to any man-in-the-middle | ✅ Fixed | Self-signed TLS via operator-generated certificate. The server auto-detects `server/certs/server.crt` and `server/certs/server.key` at startup and switches to HTTPS automatically. At build time the server reads the cert, computes the SHA-256 hash of its SubjectPublicKeyInfo (SPKI), XOR-obfuscates it, and bakes it into the agent binary alongside the other secrets. The agent sets `InsecureSkipVerify: true` (bypassing the OS CA store, which would reject self-signed certs) and substitutes a `VerifyPeerCertificate` callback that checks the SPKI pin against the baked-in value. A mismatch hard-fails the TLS handshake with no fallback. The agent also panics at startup if a pin is set but the server URL is not `https://`. HTTP is still supported as a per-build choice, useful for lab setups that don't need TLS. |
| Server response header | `Server: Werkzeug/3.x Python/3.x` response header immediately identifies the C2 server as a Flask application to any analyst inspecting traffic | ✅ Fixed | `@after_request` hook in `app.py` replaces the header with `Server: nginx/1.24.0` on every response, including error pages |

## Endpoint and binary evasion

What EDR and DFIR see on the host: process trees, artifacts, and the binary itself.

| Surface | Risk | Status | Fix |
|---|---|---|---|
| Process parentage | In `exec` mode, `cmd.exe` is gone from the process tree, but an unsigned binary directly spawning system utilities (`whoami.exe`, `ipconfig.exe`) is still visible to EDRs that monitor parent-child relationships for unsigned or unknown parents | ❌ Planned | PPID spoofing via `UpdateProcThreadAttribute`, spawning commands under a plausible parent, is the main candidate. Reflective loading was ruled out: it hides your own DLL on disk but doesn't remove the agent from the process tree, and the spawned tools (`whoami.exe` and friends) are Microsoft binaries you can't load in memory yourself. If PPID spoofing proves too noisy, document acceptance and lean on operators choosing plausible commands |
| Self-destruct cleanup artifact | On Windows, the self-destruct writes a `.bat` file to disk (`del /f /q` loop) to delete the agent binary after it exits. The batch file is a forensic artifact recoverable from disk | ❌ Planned | Keep the current deletion loop but run it as a `cmd.exe /c` one-liner instead of writing a `.bat` file to disk. Same behavior, no file artifact. `MoveFileEx` + `MOVEFILE_DELAY_UNTIL_REBOOT` was ruled out: it needs admin rights and the agent runs at user scope, and `PendingFileRenameOperations` is itself a well-known forensic check that only fires on reboot. PowerShell was ruled out too: `powershell.exe` is one of the most watched processes on the endpoint |
| Profile and OS mismatch | Nothing links `profile_id` to `target_os`: a Linux build with the Chrome/Windows profile is accepted today, and Safari on anything but macOS is always wrong. The User-Agent and `Sec-Ch-Ua-Platform` then claim an OS the host is not, an easy endpoint-side anomaly against host inventory | ❌ Planned | Enforce at build time when the selected profile's platform doesn't match the target OS, rather than warn. Build-time validation only proves build consistency: running the build on the wrong host is still operator responsibility |
| Deployed binary naming | Build artifacts are named `agent_<os>_<arch>_<hex>`. A process listing showing that name is a free flag for EDR and DFIR, and enterprise telemetry software does not look like that. Renaming after deployment is not an option: the durable state path keys on the executable path, so a rename orphans the outbox and process lock | ❌ Planned | Name the build artifact after the cover label at build time, since the `ServiceLabel` already exists, never by renaming at deploy |
| Process tree | Every shell command spawns `cmd.exe` or `sh` as a direct child, visible to any EDR | ✅ Fixed | Two execution modes give the operator control over the process tree. The default `exec` mode resolves the target binary via PATH and spawns it as a direct child of the agent with no `cmd.exe` or `sh` in between. The `shell` mode is still available for commands that need pipes or redirects, but the operator explicitly opts into it and accepts the OPSEC cost as a conscious choice rather than it being the constant behavior. |
| Function signatures | Agent functions and variables look suspicious to analysts and scanners | ✅ Fixed | Renamed all internal functions and variables to mimic benign enterprise IT software (e.g., `SyncDeviceState` instead of `checkIn`, `InstallAutoUpdater` instead of `persist`). This helps the agent blend into normal endpoint telemetry noise instead of triggering heuristics. |
| Strings in binary | Server URLs, API paths, and the persistence service name are all visible in plaintext via `strings` or Ghidra | ✅ Fixed | A random 32-byte XOR key is generated at build time by the payload builder. Every sensitive string (server URL, all API paths, the check-in sentinel, the persistence service label) is XOR-encrypted in Python, hex-encoded, and written directly into the generated `config.go` as a string literal. At runtime `funcs.ResolveConfig()` decodes them into memory on first use. Nothing sensitive appears as a printable string in the binary. |
| Build metadata / compiler footprint | Go embeds source file paths and the module name in binaries. Without extra flags, running `strings` or loading the binary in Ghidra exposes build paths like `C:\Users\<user>\Desktop\repos\C2-Project\agent\funcs\selfdestruct.go` and the original module name | ✅ Fixed | `-trimpath` strips absolute host build paths from debug info at compile time. `-buildid=` clears the per-build hash. Source files in `funcs/` were renamed to match the telemetry cover (`seal.go`, `sync_backoff.go`, `auto_updater.go`, `cache_purge.go`, `dump_sync.go`) so any residual relative paths look benign. The Go module was renamed from `c2-agent` to `endpoint-telemetry`, which is embedded in every Go binary regardless of strip flags. |
| Agent terminal output | All agent activity (beacon timing, job commands, results) was printed to stdout, immediately exposing C2 activity to anyone watching the process or terminal | ✅ Fixed | All `fmt.Printf`/`fmt.Println` calls removed from the generated `main.go` and `config.go` templates. Deployed agents are fully silent: no startup banner, no beacon output, no command or result logging. |

## Persistence

How the agent survives reboot, per OS, and the telemetry each method produces.

| Surface | Risk | Status | Fix |
|---|---|---|---|
| Windows task creation event | The COM-based scheduled task avoids `schtasks.exe` in the process tree, but when task auditing is turned on (Audit Other Object Access Events, off by default but recommended and common in enterprises), Windows writes Event ID 4698 to the Security log on task creation | ❌ Planned | Create the task by writing the task XML file directly into `C:\Windows\System32\Tasks`, bypassing the scheduler API entirely, so no 4698 is generated (the Tarrask technique). Suppressing the audit policy was ruled out: disabling the subcategory with `auditpol` writes Event ID 4719, which is louder than the 4698 it hides |
| systemd service visibility | The Linux user service sits in `~/.config/systemd/user/` as a plaintext unit file. `systemctl --user list-unit-files` lists it. File integrity monitoring catches it on write | ❌ Planned | Kept as a documented trade-off for now: no clean alternative at the user level without root, since cron is just as visible and shell rc files are watched less but weaker. May revisit later |
| macOS persistence | Not implemented. The build server rejects macOS builds with `persist_method != "none"` at compile time | ❌ Planned | LaunchAgent plist in `~/Library/LaunchAgents/`. Requires a macOS test environment. Note that execution is the harder half on macOS: the dropped binary carries a quarantine attribute, Gatekeeper and XProtect sit in the path, and macOS EDRs watch launchd registration, so getting the binary running cleanly matters more than the persistence mechanics |
| Persistence noise | `reg.exe` writes to the most-monitored Run key in Windows with a hardcoded value name | ✅ Fixed | Operator now selects the persistence method at build time. The recommended "Scheduled Task / Systemd" option uses the Task Scheduler COM API on Windows (no `schtasks.exe` or `reg.exe` child process; the COM call happens in-process) and a systemd user service on Linux (file write + `systemctl --user enable`, no `crontab` child process). The legacy "Registry / Cron" method is still available as a conscious OPSEC trade-off. Tasks and services are created under the benign name `EndpointAutoUpdate` via the XOR-obfuscated `ServiceLabel`. Detection surfaces: Windows Event ID 4698 (task creation), Linux `systemctl --user list-unit-files` and `~/.config/systemd/user/` file integrity monitoring |

## Server and infrastructure hardening

The operator side: protecting the C2 itself, its data, and its loot.

| Surface | Risk | Status | Fix |
|---|---|---|---|
| Public operator surface | Flask listens on `0.0.0.0:5000` on the same host as the Xray edge, and was proven reachable from outside during debugging. The operator API is single-factor, so a public Flask is the cheapest path to owning the framework: a scanner or stolen key queues tasks and downloads loot without touching REALITY | ❌ Planned | In REALITY deployments, bind Flask to loopback only and firewall the port, since direct HTTP and pinned HTTPS transports still need network reachability. Document the operator access path (SSH tunnel), which also removes the plaintext admin channel from the WAN |
| Plaintext storage at rest | Loot files, `c2.db`, and the agent binaries in `server/builds/` are permission-protected but unencrypted. Seizing the operator host gives up the loot, and the database holds the build AES keys, so it also burns every enrolled agent | ❌ Planned | Full-disk encryption provisioned when the host is built is the cheap answer; an encrypted loot directory is belt and suspenders. High value for real operations, low priority for the lab |
| Payload encryption | All C2 traffic payloads (commands, results) are sent as plaintext JSON, readable by any network tap | ✅ Fixed | AES-256-GCM with a per-build pre-shared key. The server generates a fresh 32-byte key at build time, injects it into the agent binary as a compile-time constant (`EncryptionKey`), and stores it in the `builds` table alongside a non-secret 8-char fingerprint (`key_id`). Every `POST /api/checkin`, `POST /api/result`, and file upload body uses the `{"kid": "...", "data": "<base64(nonce+ciphertext+tag)>"}` envelope. The GCM authentication tag prevents tampering. Each nonce is logged in a `seen_nonces` table keyed on `(kid, nonce)`; duplicate submissions are rejected with 409. A background thread purges records older than 7 days. |
| AES-GCM nonce replay | The server did not track seen nonces. A captured check-in ciphertext blob could be replayed and would decrypt to a valid (stale) payload. The server would process it as a duplicate check-in | ✅ Fixed | `seen_nonces` table stores `(kid, nonce)` pairs with a `UNIQUE` constraint. The 12-byte GCM nonce is extracted from each incoming envelope before decryption and inserted atomically with the rest of the write. Duplicates are rejected with 409. File upload replays are also blocked: the upload auth envelope binds the nonce to a SHA-256 of the file, so replaying the auth with a different file body fails the integrity check. |
| Predictable URLs | Endpoint paths (`/api/checkin`, `/api/result`) are hardcoded and easily signatured | ✅ Fixed | The server generates a random 8-character hex slug for each of the four agent-facing endpoints (check-in, result, upload, files) at first launch and stores them in the `server_config` SQLite table. The paths persist across restarts so existing agents stay connected. At build time, all four path strings are fed through the existing XOR obfuscation pipeline and baked into the agent binary, and they are never visible as plaintext in the binary, in memory, or on the wire. |
| No authentication | Every server endpoint is open, anyone who finds the server can issue commands or download loot | ✅ Fixed | A `@before_request` hook in Flask enforces a valid `X-API-Key` header on all `/api/*` requests and returns `401 Unauthorized` if it is absent or incorrect. The key is a 32-character hex string generated at first launch and stored in `server_config`. It is printed to the operator's terminal on startup. Agent-facing endpoints are naturally exempt because they live on randomised hex paths outside the `/api/` namespace. The dashboard prompts for the key on load, stores it in `sessionStorage` (wiped on tab close), and injects it as a header on every outbound API call via a centralised `apiFetch()` wrapper. |

## Capabilities and architecture

Features that are not evasion work: reach and usability of the framework itself.

| Surface | Risk | Status | Fix |
|---|---|---|---|
| Direct C2 reachability | Every agent must reach the C2 server directly. Hosts on isolated network segments with no outbound internet access cannot check in | ❌ Planned | Agent chaining: route traffic through a compromised host that does have outbound access, using it as a relay for agents that cannot reach the server directly. Treat it as a major feature, not a quick fix: it needs routing between peers, a story for hop-by-hop encryption (the per-build AES-GCM key model currently assumes agent-to-server), buffering at the relay, and handling relay death. It also has to reconcile with the REALITY inner destination being hardcoded to `127.0.0.1:5000` |
