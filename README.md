# C2 Project

> **Full technical breakdown available:** For the complete architecture review, engineering decisions, and OPSEC autopsy of every detection surface in this framework, read the blog posts: [C2 Development from Scratch: Phase 1 Teardown](https://www.hassanhamadi.me/blog/c2-development-from-scratch-phase-1-teardown) and [Fixing Every IOC: Phase 2 Walkthrough](https://www.hassanhamadi.me/blog/c2-development-from-scratch-fixing-every-ioc-phase-2-walkthrough).

C2 Project is a compact command-and-control research platform for controlled labs. It combines a Flask operator service, a browser dashboard, a SQLite data store, and generated Go agents.

Only deploy it on systems and networks you own or are authorized to test. The operator is responsible for access controls, network exposure, data handling, and legal compliance.

## Current capabilities

- Generate Windows, Linux, and macOS agents for supported Go target architectures.
- Select direct HTTP, certificate-pinned HTTPS, or REALITY with VLESS and uTLS at build time.
- Generate a fresh AES-256-GCM application key and key identifier for each build, with a separate random secret generated by each agent on first initialization.
- Queue direct-exec or shell tasks and collect authenticated, encrypted results.
- Upload files from agents, stage files for agents, and manage generated binaries from the dashboard.
- Persist agents at user scope with a Windows Run key, Windows Task Scheduler, Linux cron, or a Linux systemd user service.
- Queue authenticated self-destruction and retain a short-lived server tombstone for idempotent result acknowledgement.
- Store unsent results in encrypted, owner-only local state and retry them after restart.
- Generate and manage a self-signed server certificate for pinned HTTPS builds.

macOS builds support execution and transport features, but persistence is rejected at build time. The server is designed for a POSIX host; Windows is an agent target rather than a supported server platform.

## Architecture

```text
Operator browser
      |
      | authenticated Flask session
      v
Flask API and dashboard ---- SQLite metadata
      |                     build / loot / staged storage
      |
      +---- HTTP or pinned HTTPS --------------------+
      |                                               |
      +---- local Flask <- VLESS <- Xray <- REALITY -+---- Go agent
```

The Flask service owns agent enrollment, task state, results, builds, files, and operator authentication. Generated agents keep the existing encrypted HTTP application protocol in every transport mode. In REALITY mode, an external Xray server terminates REALITY and VLESS before forwarding the byte stream to Flask. This project does not install or configure Xray.

## Requirements

- Python 3.13 or newer (the decoy certificate-chain probe uses an API added in Python 3.13)
- Go matching the version declared in [`agent/go.mod`](agent/go.mod)
- Node.js for dashboard tests
- A POSIX-like host for the server and build pipeline
- Xray on the network edge only when using REALITY mode

Install the Python environment from the repository root:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

## Start the server

```bash
python server/app.py
```

The development server listens on `0.0.0.0:5000`. On first use it creates an operator API key and a session-signing secret in `server/c2.db`. The API key is printed at startup. Enter it at `/login`; after login, the dashboard uses an HTTP-only, SameSite=Strict session cookie. API clients can instead send the same value in `X-API-Key`.

The bundled Werkzeug server is suitable for local evaluation. Put a hardened deployment behind appropriate host and network controls. If the service is reachable over a network, use TLS or another protected administrative channel for operator access.

## Build an agent

Open the dashboard, choose **Deploy**, and select:

- target operating system and architecture
- transport mode
- callback or REALITY connection settings
- jitter range
- header profile and locale
- optional persistence method

The server compiles in an isolated temporary directory and stores the resulting binary in `server/builds/`. Configuration strings are XOR-obfuscated in generated source to reduce casual inspection; XOR is not a secret-storage boundary. The application payload itself uses AES-256-GCM, and each enrolled agent authenticates with its own random secret.

### Transport modes

| Mode | Behavior | Main requirement |
| --- | --- | --- |
| HTTP | Connects directly to the callback URL. | Reachable Flask endpoint. |
| HTTPS + pin | Connects with TLS and accepts only the SPKI SHA-256 pin embedded at build time. | Generate a certificate first and use an `https://` callback URL. |
| REALITY | Uses a uTLS ClientHello preset, authenticates to REALITY, sends a VLESS TCP request for `127.0.0.1:5000`, then carries the existing HTTP protocol in that stream. | A separately configured, reachable Xray REALITY/VLESS server. |

See [`REALITY.md`](REALITY.md) for architecture, field mapping, setup boundaries, preflight behavior, verification status, and troubleshooting.

### Persistence

| Selection | Windows | Linux | macOS |
| --- | --- | --- | --- |
| Disabled | None | None | None |
| Registry / cron | Current-user Run key | Current-user crontab | Unsupported |
| Scheduled task / systemd | Current-user Task Scheduler entry | systemd user service | Unsupported |

Persistence and self-removal run at user scope. The self-destruct path removes persistence first, then the executable and encrypted durable state. Windows uses a helper process when the running executable cannot remove itself.

## Task and result behavior

Tasks default to direct execution, which resolves a program and passes arguments without shell expansion. Prefix a dashboard command with `shell` when pipes, redirection, chaining, or other shell behavior is required. The `cd`, `get`, and `download` commands have agent-side handling:

- `cd <directory>` changes the process working directory for later tasks.
- `get <path>` uploads a regular file to the server.
- `download <file_id> <path>` retrieves a staged file assigned to that task and writes it without following a destination symlink.

A pending task is dispatched at most once and immediately becomes `sent`. If its response is lost, the dashboard marks delivery as uncertain; the operator can abandon it before deciding whether to issue a replacement. Agent results are persisted locally before submission and removed only after an authenticated acknowledgement. This protects results across ordinary restarts but does not provide exactly-once command execution.

## Security model

- Operator pages require login before dashboard HTML is served.
- Operator API routes accept either the authenticated session or `X-API-Key`.
- Agent route names are randomized and stored in the local database.
- Agent requests and server responses use AES-256-GCM envelopes with replay-nonce tracking.
- Check-ins bind a random per-agent secret to the build key that first enrolled the agent.
- Result acknowledgements bind the agent ID, task ID, report ID, and output digest.
- File transfer paths require agent identity and, for downloads, the assigned task.
- Storage helpers create sensitive directories and files with owner-only permissions.
- Pinned HTTPS checks the leaf certificate's SubjectPublicKeyInfo hash.

The local SQLite database contains operator authentication material, build encryption keys, randomized routes, agent metadata, and file records. Protect and back it up as sensitive state. Deleting it breaks existing agents. Generated binaries also contain credentials needed to connect and must be handled as secrets.

## Verification

The repository includes:

- Python regression and integration tests for server authentication, task lifecycle, build generation, storage permissions, file handling, TLS management, transport generation, replay handling, and cleanup paths
- Go unit tests for encryption, direct execution parsing, retries and durable state, process locking, downloads, cleanup, pinning, header profiles, and REALITY/VLESS framing
- Node tests for dashboard state, rendering, error handling, and request races
- a Chromium UI check when a local Chromium-compatible binary is available
- local generated-agent transport tests for direct HTTP and pinned HTTPS

The final local audit runs `python -m unittest discover`, `go test`, `go test -race`, `go vet`, the Node dashboard suite, JavaScript syntax checks, and the local transport suite. A live agent-to-Xray-to-Flask REALITY session has not been recorded, so live compatibility remains unverified. Windows code is cross-compiled and unit-tested from the development host; a live Windows run is still required for platform-specific operational assurance.

> **About the test suite:** The Python regression and integration tests in this repository were created with AI assistance during development and code review. They are primarily designed as targeted verification harnesses for specific behaviors and regressions, making them especially useful when using AI-assisted development tools to modify or audit the project. They are ordinary Python tests, however, and can also be run and inspected manually like the rest of the test suite.

## Known limitations

- The development server is single-host tooling, not a multi-tenant service or a production web stack.
- Task dispatch is at-most-once. A process or network failure after dispatch can leave delivery uncertain.
- There is no end-to-end command deadline. Dashboard result polling stops after five minutes, while the task may still complete later.
- The process lock prevents two copies of the same build path from sharing durable state, but running copied binaries creates separate state paths.
- Durable state protects queued results from restart, not from local deletion or key loss.
- Browser header profiles are static approximations. Go controls HTTP wire encoding and header order, and no claim of browser indistinguishability is made.
- REALITY uses a focused TCP/IPv4 VLESS client without UDP, multiplexing, or other VLESS commands.
- The decoy certificate check is an estimate and cannot replace a live integrated test.
- Build, loot, and staged-file deletion use retry queues, but abrupt host failure can still require operator inspection of local storage.
- Direct HTTP exposes transport metadata and should be limited to isolated labs or protected networks.

## Remaining detection surfaces and future research

The framework deliberately keeps track of behaviors that may still distinguish it from ordinary endpoint or network activity. An implemented mitigation is not the same as demonstrated indistinguishability. Items below describe remaining research areas rather than claims that every surface can or should be eliminated.

| Surface | Current state | Why it still matters | Future work |
| --- | --- | --- | --- |
| TLS and browser fingerprint consistency | **Implemented, measurement pending** | REALITY mode uses uTLS browser-family presets, but no version-matched packet capture has established that the complete ClientHello and surrounding traffic match the browser profile claimed by the HTTP layer. Direct HTTP and pinned HTTPS are separate transports and do not use the REALITY/uTLS path. | Capture controlled baseline and agent traffic with the same browser version and compare the relevant TLS fingerprint fields and observable request behavior. |
| Static browser header profiles | **Known limitation** | Browser-inspired headers are compiled into the agent, but real browser versions and header behavior change over time. Go also controls HTTP serialization details that the profile does not reproduce. | Measure profiles against current browser captures and update the profiles when differences become material. |
| Bounded beacon timing | **Known limitation** | Jitter removes a fixed interval, but repeated observations can still reveal that callbacks occur within a configured range rather than following natural application activity. | Characterize the timing distribution in packet captures and evaluate less rigid scheduling models without claiming that randomized timing alone resembles human traffic. |
| Process parentage | **Known limitation** | Direct execution removes the unnecessary shell from the process tree, but the agent remains the parent of commands it launches. Endpoint monitoring can still correlate unusual parent-child relationships. | Document the observable process tree for representative commands and evaluate the resulting endpoint telemetry in an authorized lab. |
| Windows scheduled-task telemetry | **Known limitation** | Using the Task Scheduler COM API avoids spawning command-line task-management tools, but creation of a scheduled task remains observable through normal Windows telemetry. | Measure the events produced by the current implementation and document the persistence tradeoff rather than treating absence of a helper process as absence of telemetry. |
| Linux systemd persistence | **Known limitation** | A user service is visible through the user's systemd configuration and can be detected through service enumeration or filesystem monitoring. | Document the artifacts produced by installation, normal operation, and removal in a controlled Linux environment. |
| Windows self-removal helper | **Known limitation** | Windows cannot normally remove the running executable directly, so deferred cleanup introduces a short-lived helper artifact. | Validate cleanup behavior on a real Windows host and document what remains observable during and after removal. |
| macOS persistence | **Not implemented** | macOS agents can be built without persistence, but the build server rejects persistent macOS configurations. | Add persistence only after it can be implemented and tested on an actual macOS environment. |
| Interactive sessions | **Not implemented** | The task model is asynchronous request-response. Programs requiring persistent interactive input or a TTY are outside the current architecture. | Treat interactive execution as a separate architectural feature rather than extending the existing task queue implicitly. |
| Agent relay or chaining | **Not implemented** | Agents connect to their configured HTTP(S) server or REALITY/Xray edge directly. The framework has no peer relay for systems that cannot reach that endpoint. | Evaluate relay architecture separately if segmented-network testing becomes a project goal. |
| Live REALITY behavior | **Implementation present, integration evidence pending** | The REALITY client, VLESS framing, build pipeline, and local tests are present, but a complete live agent-to-Xray-to-Flask session has not yet been recorded. Decoy behavior and packet-level similarity therefore remain unproven. | Run a controlled authorized deployment, preserve packet captures and version information, and document observed behavior separately from implementation assumptions. |
| Windows platform behavior | **Partially verified** | Windows-specific code is unit-tested where possible and cross-compiles successfully, but cleanup, locking, persistence, and file replacement have not all been exercised on a live Windows host. | Run the existing regression scenarios on a dedicated Windows test machine and record platform-specific results. |

Resolved issues such as encrypted application payloads, nonce replay handling, pinned-HTTPS validation, agent authentication, durable result acknowledgement, and server-side operator authentication are documented elsewhere in this README and are not repeated here.
